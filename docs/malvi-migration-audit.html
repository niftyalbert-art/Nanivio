The upgrade builds, but confirmed source-level security, integration and data-migration defects remain. Live calling, translation, payments and signed-in mobile screens have not been verified. This is an audit, not a certification that every function works.

What was examined

The source is the latest workspace version, not only the older GitHub Malvi branch. The initial audit captured a difference from origin/main of 136 files: 66 added, 66 modified and 4 deleted, with 12,841 insertions and 8,688 deletions. Subsequent approved repairs are described separately below. Full Git history was fetched; the two histories still do not share a common ancestor. This must be treated as a reviewed integration, not a routine fast-forward merge.

The audit covered client views and context, server route registration and authentication, realtime signaling, Agora and GetStream integration, translation/ASR/TTS services, Malvi tools and context memory, billing repositories and Paystack fulfillment, SQL migrations, settings, contacts, service features, build configuration and available tests.

A route-registration inventory found 143 Express declarations: 142 API declarations and one SPA fallback. The API declarations represent 139 unique method/path combinations; three contact operations have duplicate registrations. 81 route declarations include explicit guard middleware. This is a source inventory—not 142 successful API requests. Public catalogs, authentication endpoints and inline checks must be distinguished from genuinely missing authorization.

Evidence labels: “Passed” means an executable check actually ran. “Source-confirmed” means the relevant implementation contains the stated behavior. “Blocked/unverified” means no real authenticated/provider transaction or signed-in screen verification occurred. Security conclusions describe reachable code when the normal application is configured; the current setup-only preview intentionally disables application APIs.

No production deployment, GitHub-main merge, database migration, financial mutation, fabricated payment, simulated provider response or authentication bypass was performed. No secret values or real account data were included in this report.

Approved billing access repairs — workspace only

The user approved fixing billing access protections in the upgrade branch, without merging, deploying or changing the database. The original audit findings below describe the pre-repair source unless noted. The live Render deployment has not received these repairs.

  • All 15 administrative billing endpoints now sit behind the existing authentication middleware and a billing-specific permission guard. GET and HEAD reads require a billing-authorized administrator; writes require the appropriate finance, billing or support permission. Unknown write operations are denied by default.
  • The authenticated account's FINTECH_ADMIN permission maps to the billing engine's FINANCE_ADMIN role. Unrelated administrator roles, ordinary accounts, inactive accounts and administrators without a recognized sub-role are denied.
  • Audit identity and refund/adjustment permissions come from the verified principal, never request-body administrator claims. A support/billing dispute handler cannot promote itself to a finance administrator to issue a refund.
  • Invoice detail reads now query persistent invoices with the authenticated owner filter, accepting external invoice IDs or UUID row IDs. Other-account records return not-found. Provider earnings require the account's own or verified expert ID; business billing requires ownership or recorded administrator membership.
  • Dispute creation checks transaction ownership. Client-side billing calls send authentication and propagate rejected responses rather than hiding them as empty/success results. Fixed example provider/business IDs were removed from these private reads.
  • Malformed administrator token signatures no longer trigger unequal-length comparison exceptions. Authentication failures remain closed and do not reveal underlying provider errors.

Verification: TypeScript and production build passed. node --import tsx --test tests/billing-access.test.ts tests/setup-preview.test.ts passed all 12 tests. Coverage includes role/ownership policy inputs, 45 real local HTTP unauthenticated GET/HEAD/POST denials across the 15 admin paths, trusted actor handling, route/guard registration and client authentication/error contracts. No provider responses, payment records or financial mutations were fabricated. These tests do not substitute for a signed-in Supabase/Render end-to-end test.

The managed task preview was also restarted successfully and its proxied URL now responds with HTTP 200. It remains the setup-only screen because this task copy lacks the original deployment's configuration. No signed-in financial screen was visually verified, and the existing Render deployment was not restarted or changed.

Other audit blockers—including private chat, password-bearing application payloads, database RPC security, financial idempotency and real mobile calling/translation—are not claimed fixed by this limited repair phase.

Detailed findings and consequences

CRITICAL AT AUDIT TIME · ADDRESSED IN WORKSPACE, NOT DEPLOYED
1. Billing administration was not consistently protected

Before the approved repairs, fifteen /api/admin/billing/* declarations lacked authentication/role middleware, with no enclosing global administrator gate. They included pricing/emergency updates, dispute resolution, refund/adjustment operations, ledger/audit/user summaries and gateway/mobile-money toggles. Some handlers trusted a role or administrator name from the request body. Invoice detail and earnings endpoints also lacked appropriate authentication/ownership checks. See the approved billing-fixes section for the current workspace protections.

Consequence: once the normal app is enabled, sensitive financial reads and changes can be requested without the intended administrator identity. A protected admin page does not secure its backend. Require server-verified admin permissions and resource ownership; never trust body-supplied role declarations.

Evidence: server.ts, administrative billing block around lines 2825–3105; invoice detail around 2685. These operations were not invoked against real or fabricated financial accounts.

Live corroboration: unauthenticated HEAD requests to the pricing and overview routes returned 200 JSON headers. No financial bodies or mutations were requested.

CRITICAL · SOURCE-CONFIRMED
2. Chat messages can leave the intended conversation

Realtime chat-message/reaction broadcasting uses the global WebSocket set rather than authenticated conversation recipients. Sockets enter that set before authentication. GetStream server-token channel/message reads do not verify the requesting account's membership; the Stream webhook does not validate a provider signature.

Consequence: private chat contents and presence can be disclosed beyond their intended audience. Scope sends to authenticated, authorized members, verify read membership, validate webhook signatures and enforce privacy settings.

Evidence: src/server/realtimeServer.ts, src/server/streamService.ts, Stream routes/webhook in server.ts.

CRITICAL · SOURCE-CONFIRMED
3. Registration application payloads can preserve plaintext passwords

Expert, business and driver registration spread the submitted input into application records. The input includes the personal password. The whole application payload can be persisted and returned to registration/admin clients without removing that field.

Consequence: authentication secrets may appear in application JSON or API responses even though Supabase handles password authentication. Strip passwords and other credentials before constructing application payloads, sanitize responses and inspect existing records safely for cleanup needs.

Evidence: src/server/persistentAuth.ts, role-specific registration, profile/application persistence and application-list responses.

CRITICAL RISK · SOURCE-CONFIRMED, DATABASE GRANTS UNVERIFIED
4. Malvi's privileged credit function is insufficiently locked down

Migration 005 creates a SECURITY DEFINER credit function accepting a user, amount and command. It does not explicitly revoke execution from public/browser roles or fix the function search path. Its new account/ledger/session tables do not establish the same restrictive access pattern as the normalized billing migration. Migration 004 similarly needs table-access review.

Consequence: PostgreSQL's default public function-execution privileges can expose privileged credit commands unless external grants already prevent this. Actual database grants were not inspected. Explicitly restrict execution/table access to the service role, define safe search paths and verify RLS/permissions in staging.

Evidence: migrations/004_contacts_settings_notifications.sql, migrations/005_malvi_credit_and_usage.sql; stronger patterns appear in migrations 002 and 007.

HIGH · SOURCE-CONFIRMED
5. Credit replay and usage accounting are not atomic

The Malvi credit command changes the account balance before inserting a ledger row with conflict-ignore semantics. Reusing the same reference can therefore change a balance again while producing only one ledger entry. Application-level prechecks occur outside this transaction. Voice usage uses a new reference on retries and records consumption separately from its usage event.

Entitlement references depend on subscription ID, not subscription period; renewing a reused subscription can miss a new grant. The repository checks an ACTIVE status without consistently deriving expiry from the term. Speech can be produced before debit; caller-controlled purpose values can avoid the Malvi billing branch.

Consequence: duplicate balance changes, missed renewals, unbilled output or debits without matching usage records are possible. Use a transaction with idempotency decided before mutation, period-scoped grants, validated server-side service purpose and atomic usage/debit records. Real replay/concurrency tests are still required.

Evidence: migration 005; src/server/normalizedBillingRepository.ts; synthesize/usage routes in server.ts. No grants or charges were fabricated for this audit.

HIGH · SOURCE-CONFIRMED
6. Paid minute-pack quantity and price are client-controlled

Paystack initialization accepts the request's amount, minutes and package identifier into the order. Minute fulfillment checks the verified payment against that stored order but uses its minutes directly; the catalog lookup is used for validity, not for authoritative price/quantity. The Malvi branch does check the selected plan's catalog price, which is a useful control and should be preserved.

Consequence: a genuine but underpriced payment can be associated with an excessive minute quantity. Derive both quantity and price from a server-selected catalog package and reject unsupported packages/currencies before checkout.

Evidence: server.ts, /api/paystack/initialize and fulfillPaystackOrder, COMMUNICATION_MINUTES branch.

HIGH · SOURCE-CONFIRMED
7. Existing Supabase schemas cannot safely be upgraded by running the SQL blindly

The legacy schema and migration 002 define the same subscription, invoice and Malvi-subscription tables with incompatible shapes. Legacy IDs are text; newer definitions use UUID IDs and separate external IDs, period fields and additional mandatory columns. CREATE TABLE IF NOT EXISTS does not add missing fields or transform old rows. Later security-policy cleanup does not resolve these structural conflicts.

Consequence: applying the scripts to existing Nanivio data may leave old table shapes beneath new RPCs, fail operations or cause incompatible identifiers. Inspect the actual target schema; design explicit ALTER/backfill/conversion steps with a backup and rollback plan. Do not blindly run both schema sets.

Evidence: supabase/schema.sql versus migrations/002_billing_normalized_ledger.sql and later migrations. No target database was modified.

HIGH · SOURCE-CONFIRMED
8. Suspension, deactivation and security-session controls are incomplete

Account deletion changes profile status rather than deleting or revoking the authentication account. Sign-in rejects SUSPENDED but not DEACTIVATED; token-to-user resolution does not consistently enforce either status. Existing sessions can remain usable. “Terminate other sessions” only filters client state, not provider sessions.

Consequence: the UI can promise account/session restrictions that the server does not enforce. Define deactivation versus deletion, revoke or deny sessions accordingly, and implement actual session revocation. Also decide whether automatic email confirmation and the separate OTP endpoints meet the intended verification policy.

Evidence: src/server/persistentAuth.ts and src/context/NanivioContext.tsx, terminateOtherSessions.

HIGH · SOURCE-CONFIRMED
9. Account top-up and transfer can display false success

The Account top-up handler does not validate the HTTP or application response. Its endpoint intentionally returns 503 when no real payment path is used. The transfer handler calls a nonexistent /api/billing/transfer route; a resolved HTTP 404 still leads to its success message. Account-deactivation response handling also needs validation.

Consequence: a user can be told money was added or transferred when it was not. Connect the proper authorized workflow, check both status and payload, and only display success after confirmed server/provider completion.

Evidence: src/components/account/AccountView.tsx, top-up/transfer handlers; server route inventory.

HIGH · SOURCE-CONFIRMED
10. Several translation/speech clients omit required authentication

Generic translation and multiple MT/TTS helpers send only content-type headers, and the speech-token request lacks the bearer token. The backend expects a token, not an implicit browser cookie. Main Malvi chat, transcription and speech calls do send bearer authentication, so the fault does not affect every path equally. Malvi action-confirmation requests also omit the needed token.

Consequence: signed-in users can still receive 401 errors. Centralize authenticated API access and test every caller against the protected endpoint rather than bypassing authentication.

Evidence: src/lib/translator-engine/engine.ts, MT/TTS adapters, src/lib/audio/ttsAudioGenerator.ts, src/services/speechService.ts, action confirmation in MalviView.tsx.

HIGH · SOURCE-CONFIRMED
11. Ordinary-user features do not receive consistent capability configuration

Client feature flags initialize disabled. The feature/pricing synchronization effect is limited to administrators, while ordinary-user call initiation depends on those flags. Server feature objects omit several keys expected by the client, including the floating Malvi feature.

Consequence: valid non-admin accounts can have calling or Malvi entry points disabled even after providers are configured. Supply an authenticated, non-sensitive capability endpoint for every role, normalize missing keys and persist administrator changes.

Evidence: src/context/NanivioContext.tsx, feature initialization/synchronization and call guards; server.ts, feature dictionary; MalviFloatingWidget.tsx.

HIGH · SOURCE-CONFIRMED
12. Group-call signaling and channel access need correction

The client sends invitations to multiple recipients with one call ID, but the server's active-call duplicate check rejects subsequent invitations and tracks one recipient. Agora membership enforcement is tied to the one-to-one channel prefix, leaving group-channel authorization too broad.

Consequence: a displayed group call is not proof all participants were invited or authorized. Model group membership explicitly and validate token/join access for both channel types.

Evidence: src/context/NanivioContext.tsx, group initiation; src/server/realtimeServer.ts, active-call map; Agora token/join routes in server.ts.

HIGH · SOURCE-CONFIRMED
13. Call lifecycle state can outlive the actual connection

Socket-close handling removes presence but does not end active calls or notify peers. There is no authoritative server ringing expiry. Group timeout clears local state without ending the server call. Decline can leave the channel-participant registry behind. Acceptance sets the UI connected before the media join promise is verified.

Forced termination updates in-memory membership and sends a signal; it is not a demonstrated provider-side media eviction. Already-issued tokens can remain valid until expiry.

Consequence: stuck ringing, stale channels, misleading connected status and continuing media/billing are possible. Add server-owned timeout/disconnect transitions, cleanup and verified media-join/error handling; validate provider termination semantics.

Evidence: src/server/realtimeServer.ts, src/context/NanivioContext.tsx, src/lib/agoraClient.ts.

HIGH · SOURCE-CONFIRMED
14. Local history and memory are not isolated for shared-device accounts

Chats, contacts, call logs and Malvi history use global browser-storage keys. Sign-out clears authentication but does not reset all those stores. Missed-call logs are browser-local, so offline and cross-device records are not reliably delivered.

Malvi's context snapshot can include wallets, recent transactions, contact/provider details and recent conversation content sent to Gemini. This is sensitive context sharing, not a durable server memory system.

Consequence: another account using the same browser may encounter prior-account data; users can lose history on another device. Account-scope storage, clear/reset state on identity change and minimize/consent-control provider context. Add server-persisted call outcomes for reliable missed calls.

Evidence: src/context/NanivioContext.tsx, localStorage/signOut/context-memory construction; MalviView.tsx; MissedCallsModal.tsx.

HIGH · SOURCE-CONFIRMED
15. Some Malvi interfaces still substitute canned output

The floating widget answers keyword-based prompts after a timer rather than calling Gemini. Main Malvi and business-collaboration clients can replace a failed provider request with reassuring preset text. The business action-item list is fixed rather than parsed from the model's output.

Consequence: users can mistake failure or demo logic for real AI, completed actions or genuine business recommendations. Surface explicit errors, keep prior valid output distinct and only present actions actually returned and validated. The backend's explicit 503/502 failure behavior is worth retaining.

Evidence: MalviFloatingWidget.tsx, error paths in MalviView.tsx and MalviBusinessCollaborationRoom.tsx, Malvi/business server routes.

HIGH · SOURCE-CONFIRMED
16. Tool and subscription response contracts do not match their clients

A valid tool-only response can be dropped because the client requires nonempty reply text. The “money” navigation target differs from the app's “billing” view. Unknown Malvi actions can return success without doing anything.

Persistent Malvi subscriptions return video-minute fields while the UI expects video-interaction-minute fields. Usage responses return consumed/remaining credit, but the client only updates when a subscription object appears. Type casts hide these discrepancies.

Consequence: valid tools disappear, navigation fails and quotas display incorrectly or stay stale. Introduce validated request/response schemas, adapt subscription fields and reject unknown actions explicitly.

Evidence: Malvi routes/controller, MalviView.tsx, App.tsx, src/server/normalizedBillingRepository.ts, billing-client/context usage handlers.

HIGH · SOURCE-CONFIRMED
17. Translation coverage and metering claims exceed the demonstrated behavior

The 18-language catalog includes international languages, Ghanaian language codes and Swahili/Luganda. Azure, Khaya and Sunbird routes are real integration code, but generic ASR currently always throws. Continuous Azure speech and browser voice-note recognition do not establish equivalent coverage of the Ghanaian paths. Static provider “online,” latency and confidence metadata are not health measurements.

Single translation can return a truthful failure; fan-out can count original unchanged text as a successful translated result. Translation/chat-webhook usage is not independently quota-gated; call/session elapsed-time reporting is not a substitute for metering each billable provider operation.

Consequence: users can receive untranslated content labelled successful, and provider costs may occur outside tracked quotas. Separate measured availability from static capability, use per-language failure results and server-authoritative service metering.

Evidence: translator-engine ASR/router/catalog/providers, speech/voice-note services and server.ts translation/fan-out/Stream routes.

HIGH · SOURCE-CONFIRMED
18. Legacy and normalized billing paths can diverge

The upgrade combines a persisted legacy financial snapshot with normalized tables/RPCs. Some administrator changes still write the snapshot while user reads come from normalized tables; legacy user lookup may not find Supabase accounts. Snapshot writes do not establish multi-instance conflict safety. Transaction/invoice rows are snake_case while client interfaces expect camelCase; a missing mapping can suppress fields. One usage read returns zero on database error.

Consequence: balances, plans, invoices and admin views may disagree, and database failures can look like zero usage. Choose one authoritative write path, explicitly adapt response shapes and fail visibly on unavailable billing data.

Evidence: src/server/billingPersistence.ts, normalized repository, administrator grant paths and billing responses in server.ts.

MEDIUM · SOURCE-CONFIRMED / MOBILE UNVERIFIED
19. Media lifecycle and mobile performance need real-device checks

Speech stop behavior is incomplete; recognizer shutdown/audio-URL cleanup have paths that do not reliably release the original resources. Malvi microphone processing uses deprecated ScriptProcessor behavior. The client build is large and several dynamically imported audio services are also statically imported, defeating splitting. The avatar asset is approximately 665 kB.

Consequence: interruption, navigation and repeated sessions may leak microphone/audio resources; first load can be slow on mobile networks. Exercise permission denial, backgrounding, stop/restart, Bluetooth/speaker changes and failed playback; split heavy views without claiming performance improvements before measurement.

Evidence: src/services/speechService.ts, audio generators, Malvi microphone implementation and build output.

MEDIUM · SOURCE-CONFIRMED
20. Some presented capabilities remain unavailable or local demonstrations

Ride/rental booking, fintech rails, live FX and telecom fulfillment explicitly lack provider connections. Driver cockpit local status transitions and SOS messages are not backed by real dispatch/emergency services. Business participants/ideas/tasks are local state, not a synchronized team room. The avatar is an animated 2D stage, not 3D video generation.

Consequence: the migration must distinguish working interfaces from working services. Hide or clearly label unavailable/demo operations and do not imply a booking, transfer, emergency dispatch or shared collaboration happened.

Evidence: services/fintech/telecom backend routes, driver UI, business-collaboration component and avatar implementation/documentation.

MEDIUM · SOURCE-CONFIRMED
21. Operational status is not evidence of production readiness

The production-status route labels production true and largely checks configuration presence, not successful provider connectivity. Its critical-provider set does not represent every service needed for the claimed language coverage. Normal health can be OK while optional capabilities are unusable. The current managed preview additionally has a port conflict.

Consequence: distinguish process health, database health and per-feature verified readiness. Fix the managed preview lifecycle, replace static status claims with accurate configuration/health information and retain fail-closed production behavior.

Evidence: production-status/health/startup code, workflow output and direct/proxied development requests.

Controls worth retaining

  • The production server refuses in-memory financial operation; unconfigured development exposes only an honest setup screen and blocks normal APIs/WebSockets.
  • Real provider adapters exist; main Malvi server routes explicitly fail rather than inventing provider results.
  • Paystack fulfillment uses durable order references and a verified/signed-provider flow; Malvi plan fulfillment checks catalog price. These controls still need genuine replay/concurrency/payment tests.
  • Communication entitlement code preserves consumption and the existing term during self-service tier/cycle changes rather than issuing a fresh allowance on every switch.
  • Responsive Account and missed-call source changes, typed routing metadata, mobile-focused controls and a production PWA build provide useful foundations—but are not signed-in UI verification.
  • The default gemini-3.8-flash model is listed in the current official Gemini model documentation. It was not incorrectly flagged as an invalid model based on outdated assumptions. This does not verify this application's access or output. Source: official Gemini models documentation.

How to migrate without losing existing Nanivio behavior

  1. Distinguish the existing deployment from staging. The Render upgrade already reports Supabase/Agora configuration. Use that existing deployment for approved live checks; separately resolve the task preview's port conflict and missing access if staging is needed. Do not recreate providers, remove authentication or enable fake data to make screens appear.
  2. Fix the access and privacy blockers first. Protect all admin/financial routes, filter chat recipients and reads, sanitize role applications, restrict privileged database functions and enforce account status.
  3. Repair truthful integration behavior. Use authenticated client calls; validate success responses; remove canned failure substitutes; fix capability delivery, tools/contracts, group signaling and server call cleanup.
  4. Inspect and upgrade the existing database explicitly. Back up the target; inventory schemas, policies, grants and row counts; prepare reversible field/ID conversions and backfills. Review migrations 001–007 against actual existing objects. Do not replace the database or blindly concatenate the old schema and new migrations.
  5. Consolidate financial authority. Make catalog prices/quantities server-derived, enforce idempotent atomic consumption, normalize client data contracts and retire conflicting legacy write paths. Preserve existing users, Nanivio numbers, balances, subscriptions, payments and invoices.
  6. Prepare an integration branch from GitHub main. Compare the full latest-workspace delta, reconcile unrelated histories deliberately, retain existing Nanivio payment/auth behavior unless an approved business change replaces it, and remove dead duplicate handlers.
