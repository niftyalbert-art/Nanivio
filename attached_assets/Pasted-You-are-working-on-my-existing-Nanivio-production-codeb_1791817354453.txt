5. LANGPRETATION COMMUNICATION SUBSCRIPTION PLANS
=================================================

IMPORTANT NEW REQUIREMENT.

Nanivio has Communication subscription plans for Langpretation.

When a user selects ANY Langpretation Communication plan, the system must automatically grant the communication credit associated with that plan.

CRITICAL BUSINESS RULE:

Selecting the Langpretation Communication plan itself grants the user's communication credit.

The user DOES NOT need to make a Paystack subscription payment for this credit to be granted.

Therefore:

User selects plan
↓
System records the selected plan
↓
System automatically credits the user's communication/Langpretation credit balance
↓
User can use the granted communication credit

There must NOT be a Paystack payment requirement between plan selection and credit allocation for this specific Langpretation Communication-plan flow.

Do not redirect the user to Paystack merely to grant these credits.

Do not mark the credit as paid when no payment occurred.

Do not fabricate a Paystack transaction.

Do not create a fake payment reference.

The system should distinguish between:

1. PLAN SELECTION / CREDIT GRANT

and

2. ACTUAL PAYSTACK PAYMENT TRANSACTION

The first must work without payment.

The second should only occur where an actual paid transaction is intentionally required elsewhere in the existing Nanivio billing architecture.

IMPORTANT:
Do not break existing Paystack functionality for other products, subscriptions, deposits, billing or payment flows.

Determine how the current billing database/state is structured and integrate this requirement into the existing architecture rather than creating an unrelated parallel credit system.

The credit grant should be:

* tied to the authenticated user
* tied to the selected communication plan
* recorded persistently
* reflected immediately in the user's balance/usage state
* available to Langpretation
* protected against accidental duplicate crediting caused by repeated clicks/reloads where appropriate
* auditable
* compatible with existing billing/usage records

If the existing system already has a credit ledger, wallet, usage balance, subscription record, or communication-minute system, reuse it rather than creating unnecessary duplicate state.

Determine whether the plan selection should create:

* a subscription record
* a credit allocation/ledger entry
* a usage allowance
* an entitlement

based on the existing architecture.

Do not guess. Inspect the existing implementation first.
